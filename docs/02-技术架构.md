# 技术架构文档——《失控因子》Unstable Factor

> 引擎：Godot 4 · 语言：GDScript · 版本 v0.1
> 本文档描述工程结构、核心系统与数据流，不包含具体实现代码。

---

## 1. 技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 引擎 | Godot 4.x | 免费开源、2D 能力强、GDScript 上手快、导出多平台 |
| 语言 | GDScript | 引擎原生、迭代快，性能敏感处可用 C#/GDExtension 补充 |
| 渲染 | 2D（Node2D / TileMapLayer / Sprite2D） | 2D 肉鸽，无需 3D |
| 物理 | CharacterBody2D + Area2D（自行控制移动手感） | 动作肉鸽需要自定义手感，不全依赖物理模拟 |
| 数据 | 自定义 Resource(.tres) + JSON/CSV 导入 | 强类型 + 批量编辑（见 §6.3） |
| 存档 | JSON（`user://` 目录） | 简单可读、跨版本迁移方便 |

## 2. 总体架构分层

采用 **"数据层 / 逻辑层 / 表现层" 三层分离**，逻辑尽量与场景解耦，便于测试与换皮。

```
┌─────────────────────────────────────────────┐
│  表现层（View）                               │
│  场景 .tscn、Sprite2D、动画、特效、音效、UI     │
└──────────────────────┬──────────────────────┘
                       │ 信号 / 事件（EventBus）
┌──────────────────────▼──────────────────────┐
│  逻辑层（Logic）                              │
│  战斗结算、词条/状态效果、因子系统、AI、         │
│  程序化生成、肉鸽循环状态机                     │
└──────────────────────┬──────────────────────┘
                       │ 读取 / 查询
┌──────────────────────▼──────────────────────┐
│  数据层（Data）                               │
│  因子/怪物/技能/词条/房间/事件/对话 数据表       │
└─────────────────────────────────────────────┘
```

**核心原则**：
- **逻辑不依赖场景**：战斗结算、词条计算等写为纯 GDScript 类/RefCounted，可在无场景下测试。
- **表现通过事件驱动**：逻辑只发信号（如 `damage_dealt`、`modifier_added`），由表现层订阅播放动画/音效。
- **全局通信走 EventBus**：避免节点间硬引用。

## 3. 目录结构（feature 导向）

```
res://
├── project.godot
├── autoload/                  # 全局单例（见 §4）
├── boot/                      # 启动、加载、初始化流程
├── player/                    # 玩家：场景、控制器、属性
├── enemies/                   # 敌人：场景、AI、属性
├── combat/                    # 战斗：命中判定、伤害结算、投射物、预警
├── modifiers/                 # 词条/状态效果（Buff/Debuff）系统
├── factors/                   # 因子系统：注射、失控值、因子词条
├── rooms/                     # 房间：场景、程序化生成、房间图
├── chapters/                  # 章节：章节配置、章节地图
├── run/                       # 单局循环：RunManager、奖励、掉落
├── meta/                      # 局外：永久成长、图鉴、难度
├── story/                     # 剧情：对话、事件、演出
├── ui/                        # 通用 UI：HUD、面板、菜单
├── data/                      # 数据表资源（.tres / .json / .csv）
├── shaders/                   # 着色器
├── art/                       # 美术资源（纹理、动画、字体）
└── audio/                     # 音频资源
```

> 说明：目录按 **feature（功能域）** 组织而非按文件类型，便于同一功能的场景+脚本就近维护。

## 4. Autoload 单例设计

Godot 的 `autoload` 用于全局系统。推荐以下单例（职责单一、按需加载）：

| 单例 | 职责 | 关键接口（示意） |
| --- | --- | --- |
| `GameManager` | 顶层游戏流程状态机（启动→主菜单→单局→结算→局外） | `change_state()` |
| `EventBus` | 全局事件总线（信号中心，逻辑与表现解耦） | `emit(name, payload)` / `on(name, cb)` |
| `DataManager` | 加载/缓存/查询所有数据表（含共鸣表/污染表） | `get_factor(id)` / `get_rows(table)` |
| `BuildManager` | v0.2 六边形情绪构筑：槽位/相邻检测/共鸣/乘法稀释/情绪污染/情绪过载 | `place_factor()` / `dilution()` / `dominant_pollution()` |
| `RunManager` | 单局状态：章节/房间/精华/货币 + v0.2 双轨资源（理智/失控）与临界状态机 + 动态难度 + 记忆碎片结算 | `start_run()` / `inject_factor()` / `tick()` |
| `SceneManager` | 场景切换、加载、过渡（延迟到帧末执行） | `goto(scene, params)` |
| `SaveManager` | 存档读写（局外进度 + 设置 + 单局中断） | `save()` / `load()` |
| `MetaManager` | 局外成长：核心货币 + 永久强化 + v0.2 记忆碎片（禁因子/预设共鸣） | `toggle_ban()` / `cycle_preset()` |
| `AudioManager` | BGM/音效管理、音量、淡入淡出 | `play_sfx(id)` |
| `PoolManager` | 对象池（子弹/特效/敌人实例复用） | `acquire(type)` / `release(obj)` |

> 原则：**单例之间也通过 EventBus 通信**，减少相互硬依赖；单例只做"编排/协调"，具体逻辑下沉到对应系统的类里。

- 场景切换统一走 `SceneManager`，支持加载过渡与参数传递。

## 6. 核心系统设计

### 6.1 游戏流程状态机（GameManager）

状态：`Boot → MainMenu → Run → GameOver / Victory → Meta → ...`

- 用状态机管理顶层流程，避免各界面互相跳转耦合。
- 单局内再嵌套一层 `RunStateMachine`（探索 / 战斗 / 结算 / 事件 / 商店 / 死亡）。

### 6.2 事件总线（EventBus）

- 定义全局事件命名规范，例如：
  - `combat.damage_dealt`、`combat.entity_died`
  - `run.modifier_added`、`run.instability_changed`
  - `room.cleared`、`ui.toast`
- 逻辑层只 `emit`，表现层（音效、动画、HUD）`on` 订阅，**彻底解耦**。

### 6.3 数据管理（DataManager）

- **定义**：用 Godot 自定义 `Resource` 类定义各表结构（强类型 + 编辑器可视化）。
- **内容**：用 JSON/CSV 批量编写，运行时由 `DataManager` 解析并缓存为 `Resource`（或直接读 JSON）。
  - 好处：策划/文案可用表格工具批量改内容，无需碰引擎。
- 数据表清单见《03-数据表设计》。

### 6.4 战斗结算系统（Combat）

- **伤害管线**（与 GDD §6.2 一致），由独立的 `CombatResolver` 负责，不写死在角色里：
  ```
  attack → hit_check → 暴击/加成(modifiers) → 抗性/护甲 → apply_damage
         → on_hit_effects → death_check → on_death(掉落/触发)
  ```
- **词条（Modifier）**作为管线中的可插拔计算单元（见 §6.5）。
- **投射物/命中**用 Area2D 或自定义碰撞查询；**敌人预警**用可复用 TelegraphedAttack 组件。

### 6.5 词条 / 状态效果系统（Modifiers）

- 所有 Buff/Debuff、因子词条、装备词条统一抽象为 **Modifier**：
  - 属性修饰（`+攻击力`、`攻速x1.2`）
  - 行为钩子（`on_hit`、`on_kill`、`on_tick`、`on_take_damage`）
  - 定时/层叠（持续时间、叠层上限、刷新规则）
- 用**优先级 + 阶段**控制结算顺序，避免词条间冲突。
- 这是肉鸽构筑的技术基石，优先级最高。

### 6.6 因子系统（Factors）

- 因子 = 一组 `Modifier` + 主动技能 + 主题标签的**集合（Bundle）**。
- `RunManager.inject_factor(factor_id)`：应用因子词条 → 累积失控值 → 检查失控阈值。
- **失控值（Instability）**：
  - 独立进度条，随注射/事件增减；
  - 达到阈值触发**失控词条**（随机负面 Modifier）或**失控状态**；
  - "稳定剂"道具可降低失控值。

### 6.7 怪物 AI

- 采用 **行为树（Behavior Tree）或有限状态机（FSM）** 组织 AI，推荐先 FSM（简单够用），复杂度上升再迁行为树。
- 通用 AI 骨架：`巡逻/待机 → 索敌 → 追击 → 攻击（可读前摇）→ 受击/硬直 → 死亡`。
- 每章怪物的差异化通过**数据配置（词条 + 行为参数 + 主题技能）**实现，而非为每章写新 AI。

### 6.8 程序化生成（Rooms）

- 房间内容由**种子随机**：怪物组合、奖励、事件、房间拓扑。
- 分两层生成：
  1. **关卡图**：生成房间节点图（保证 Boss 房在末尾、可通行）。
  2. **房间内**：TileMap 布局 + 刷怪点 + 交互物。
- 所有随机统一用 `RandomNumberGenerator` + 种子，保证可复现（用于调试与分享种子）。

### 6.9 存档系统（SaveManager）

- 三类数据分开存：
  1. **设置**（音量、键位、画质）
  2. **局外进度**（meta 成长、图鉴、剧情解锁、难度）
  3. **单局中断**（可选：中途退出可续）
- 格式 JSON，写入 `user://`；做版本号字段便于未来迁移。

### 6.10 UI 系统

- HUD 与面板用 Godot Control 节点搭建，UI 只订阅 EventBus 展示数据，不持有游戏逻辑。
- 关键面板：HUD（HP/SAN/失控值/技能冷却）、词条面板、商店、事件弹窗、暂停/设置。

### 6.11 剧情 / 对话系统

- 对话用**数据表驱动**（对话节点、说话人、选项、条件、后果），由 `story/` 下通用对话播放器渲染。
- 支持：短对话、选项分支、事件后果（改失控值/资源/词条）、跳过。

### 6.12 音频系统

- `AudioManager` 管理 BGM（每章主基调）与音效（打击/预警/UI），支持音量与淡入淡出。
- 通过 EventBus 触发（如 `combat.hit` → 播放对应音效）。

### 6.13 对象池（PoolManager）

- 高频实例（子弹、命中特效、飘字、敌人）用对象池复用，减少 GC/实例化开销。
- 适合战斗密集场景，属性能优化项（非首版必需，但接口先预留）。

## 7. 关键数据流（示例）

### 7.1 玩家注射因子

```
UI 点击注射
  → RunManager.inject_factor(factor_id)
  → DataManager.get_factor(factor_id) 取因子 Bundle
  → ModifierSystem 应用词条（加 Buff）
  → 累积失控值 → EventBus.emit("run.instability_changed")
  → HUD 更新失控条 + 失控阈值检查（可能触发负面词条）
```

### 7.2 一次击杀

```
Enemy 血量归零
  → CombatResolver 判定死亡
  → EventBus.emit("combat.entity_died", enemy)
  → 表现层：播放死亡动画/音效/掉落
  → RunManager：结算掉落（因子精华/货币/词条）
  → HUD / 房间系统更新（是否清房）
```

## 8. 输入系统

- 使用 Godot **Input Map**（`project.godot` 中的动作定义），统一抽象为动作名（`move`、`dash`、`attack`、`skill_1`、`interact` 等）。
- **俯视角 + 发射型**：默认键鼠（WASD/方向键移动、鼠标瞄准、左键发射、右键技能、空格冲刺）；动作名设计兼容双摇杆，手柄支持留到 M7。
- UI 导航单独处理。

## 9. 关键设计决策记录

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 架构范式 | Godot 原生 Node + 组件组合 + 信号，**不引入 ECS 框架** | 2D 肉鸽体量下更易维护、Godot 生态友好、开发效率高 |
| 逻辑/表现分离 | 通过 EventBus + 纯逻辑类实现 | 便于测试、换皮、多人扩展 |
| 内容管理 | 数据驱动（数据表 + Resource） | 8 章大量内容需要策划可批量编辑 |
| 词条系统 | 统一 Modifier 抽象 | 因子/技能/装备复用同一套，构筑深度的技术基础 |
| 视角 | 俯视角（上帝视角）+ 键鼠瞄准 | 适配发射型武器与走位战斗，明确 2D 平面坐标体系 |
| 美术 | 像素风 | 统一低饱和 + 每章情绪主题色；剧情演出可更细腻 |
| 玩家武器 | 因子能量发射型（投射物） | 以投射物/弹幕为核心，因子改变发射形态 |
| 平台 | PC 单机 | 首日不做多人/手柄，动作名预留兼容 |
| 命名 | 《失控因子》Unstable Factor | 呼应"情绪因子 + 失控值"核心 |
| 存档 | JSON + 版本号 | 简单、可读、易迁移 |

## 10. 性能注意事项

- 优先对象池化高频对象；限制同屏敌人数量（房间式地牢天然可控）。
- 逻辑层用 RefCounted 纯类，避免每帧大量 Node 信号开销。
- 特效/动画用 GPU 友好的粒子与 shader，避免过多 Node 计时器。
- 首版以"流畅 60fps"为目标，性能优化不提前过度设计。

## 11. 首次搭建顺序（工程骨架）

1. 建 Godot 4 工程 + 目录结构 + 8 个 Autoload 空壳。
2. 打通 `EventBus` + `SceneManager` + `GameManager` 状态机。
3. 搭一个最小可玩房间（玩家移动 + 一只怪 + 一次伤害结算）。
4. 接入 `DataManager` 与 `Modifier` 系统（从一两个词条开始）。
5. 再做因子注射 + 失控值，形成完整核心循环。
